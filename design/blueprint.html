Sheltr Blueprint

A flood survivor uploads photos of a damaged room. An agent on Vultr turns them into a 3D room, finds and prices the damage, and fills in the aid application. Every risky step runs inside a throwaway sandbox, and nothing is submitted until the survivor approves it.

01The big picture

There are four parts. The web app is what people see. VM 1 is the brain: it plans, keeps the case, and holds every secret. VM 2 is the blast zone: every piece of code and every browser run happens there, in a sandbox that gets destroyed afterwards. Vultr Serverless Inference is the model that thinks.

02What the survivor does

This is the product from the user's side. It is also the order of the live demo.

03Under the hood, step by step

The same journey as messages between the parts. Read it top to bottom. The model never runs anything itself; it only suggests. VM 1 decides, and VM 2 executes in a sandbox.

04Inside a sandbox

Every task gets a brand-new sandbox, and every sandbox ends the same way: destroyed. Whatever happens inside, good or bad, the outputs are copied out and the sandbox is thrown away.

05The code loop (Pattern A)

The model writes real code, the sandbox runs it, and errors go back to the model. This retry loop is shown live on screen, because the brief asks for it.

06The browser loop (Pattern B)

A real browser inside a sandbox fills in the form one step at a time. After every step a vision model checks the screenshot. The final submit always waits for a person.

Why a mock portal

The agent must never submit to a real government website during a hackathon. You build a small multi-step aid form on VM 1 and the agent fills that in. Everything else about the browser run is real.

07The containment moment

The brief requires one on video. After every disaster, scammers text survivors links to lookalike aid websites that steal bank details. When a survivor asks Sheltr to check one, the agent opens it in a throwaway browser sandbox, and the site attacks. Each attack hits a wall.

08What you set up on Vultr

Do these in order. Pick one region for everything. The inference models are listed in Atlanta, so an Atlanta region keeps model calls fast.

  1. Redeem the $200 credit required

    Use the coupon from the organisers' email. Never post the code anywhere.

  2. Create a VPC (private network) required

    Both VMs join it. This is how VM 1 talks to VM 2 without VM 2 having public ports.

  3. VM 1 · Control plane required

    Cloud Compute, Ubuntu 24.04, 2 vCPU and 4 GB. Attach the VPC. Firewall: allow 443 and 80 from anywhere, 22 from your IP only.

  4. VM 2 · Sandbox host required

    VX1 (it exposes KVM, which microVMs need), Ubuntu 24.04, 4 vCPU and 8 to 16 GB for the depth model. Attach the VPC. Firewall: no public ports except 22 from your IP. The runner listens on the VPC address only.

  5. Serverless Inference key required

    Turn on Serverless Inference and create an API key. Put it in VM 1's environment only. Test one chat call and one image call.

  6. HTTPS address required

    Caddy on VM 1 gets a free certificate automatically. With no domain, a name like 1-2-3-4.sslip.io (your VM 1 IP with dashes) works.

  7. Vultr API key optional

    Only for the throwaway-instance extra: VM 1 creates a fresh VM for the browser task and deletes it afterwards. Restrict the key to VM 1's IP.

  8. NetBird optional bonus

    Serve the app through NetBird so VM 1 needs no open ports either. Only if time allows.

First commands on VM 2, from Vultr's sandboxing guide:

curl -fsSL https://install.microsandbox.dev | sh
sudo usermod -aG kvm $USER && newgrp kvm
msb doctor
msb create --name test01 --cpus 1 --memory 256M debian
msb exec test01 -- uname -a
msb stop test01 && msb remove test01

Model call from VM 1 (the API is OpenAI-compatible):

export OPENAI_BASE_URL=https://api.vultrinference.com/v1
export OPENAI_API_KEY=$VULTR_INFERENCE_API_KEY
# model: glm-5.3 (text + images + tool calling). Check the live list first:
curl https://api.vultrinference.com/v1/models
Where secrets live

The inference key and the Vultr API key sit in VM 1's environment and nowhere else: not in a sandbox, not in the browser, not in the GitHub repo. The venue Wi-Fi password in Hackathon.txt stays out of the repo too.

10Build order

Riskiest first. If time runs out, everything built so far still demos.

  1. Vultr setup and a sandbox that runs

    Steps 1 to 5 of the Vultr list. Done when msb exec prints uname from inside a microVM. About 45 minutes.

  2. Depth model in the sandbox

    One real photo in, room.glb out. This is what makes the 3D real, so it goes first. About 60 minutes.

  3. Runner service on VM 2

    Create with limits, stream logs, copy outputs, destroy. About 45 minutes.

  4. Control plane on VM 1

    Case API, planner with tools (run_code, run_browser, ask_approval), retry loop, WebSocket. About 90 minutes.

  5. Browser sandbox and mock portal

    Playwright fills the form, vision check per screenshot, approval gate. About 60 minutes.

  6. Wire the 3D UI to real data

    Load the real room.glb, real markers and real log events into the mockup scene. About 60 minutes.

  7. Containment demo and deliverables

    Poisoned photo, README with these diagrams, public URL, one-minute video, submit. About 45 minutes.

If you are short on time: run sandboxes on VM 1 instead of a second VM, use a pre-made room.glb instead of the live depth model, and skip NetBird. Keep the code loop, the browser loop and the containment moment real.

11Words used here

Control plane
The server that plans and gives orders. It never runs risky code itself.
Sandbox
A sealed box where code runs. If the code is dangerous, only the box is harmed, and the box is thrown away.
microVM
A tiny virtual machine with its own kernel. The strongest kind of sandbox on Vultr's list.
gVisor
A layer that makes a normal Docker container much harder to break out of.
Microsandbox
The open-source tool Vultr's guide uses to create and destroy microVMs with one command.
Depth model
An AI model that estimates how far away every pixel in a photo is. That turns a flat photo into 3D.
Playwright
A tool that drives a real web browser from code: open pages, click, type, take screenshots.
Vision model
A language model that can also look at images, used here to read the damage and check screenshots.
WebSocket
A connection that stays open so the server can push live updates to the web app.
VPC
Vultr's private network between your VMs. Traffic on it never touches the public internet.
Pattern A / B
The brief's two required ways of working: A runs code in a sandbox, B drives a browser in a sandbox. We do both.
