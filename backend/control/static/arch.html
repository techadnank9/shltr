One case, step by stepWhat happens after a survivor uploads one photo.

  1. Upload, sealed offThe file is opened only inside a photo microVM: decoded there, EXIF stripped, re-encoded. Everything after this sees only the clean copy. A video gives its sharpest frame.
  2. 3D roomDepth Anything V2 (metric indoor) estimates metres per pixel and builds a textured mesh of about 268k vertices. No network inside.
  3. Find and price the damageglm-5.3 on Vultr Serverless Inference returns the damaged items, boxes, severity and cost.
  4. Measure it (Pattern A)glm-5.3 writes Python that ray-casts onto the mesh. It runs in a fresh microVM; if it fails, the error goes back and the agent retries, visibly.
  5. Evidence reportA report microVM builds a 4-page PDF: photo, damage table, 3D views, SHA-256 fingerprints, sandbox ids.
  6. Check a scam linkA browser microVM opens the link. The forced download is captured in quarantine; the data-theft request is blocked by the allowlist. The model gives a verdict.
  7. Fill the claim live (Pattern B)A browser microVM fills the mock aid portal and streams a screenshot after every action. The vision model checks each step. It stops before Submit.
  8. Human gateThe survivor sees every field the agent typed, can edit any of them, then approves. "Not yet" keeps the draft.
  9. Submit in a fresh microVMA new browser microVM types the approved values, submits and returns the receipt. Every microVM is destroyed.

ContainmentWhat each sandbox can and cannot do.

MicroVM, not a container

Each job gets its own Microsandbox microVM with its own kernel, on a VX1 with hardware virtualization. Created for one job, destroyed afterwards.

Network off by default

Every microVM starts with no network. One allow rule is added per job: the runner, or the mock sites for the browser. Nothing else is reachable.

No secrets inside

API keys live only on VM 1. Input is mounted read-only, output goes to a separate folder, and CPU, memory and time are capped.

Forced download → held

The scam page's download lands in quarantine inside the browser microVM. We report its name, size and SHA-256; it dies with the VM.

Data theft → blocked

The page's POST of the survivor's details to an outside server fails on the allowlist. The blocked request is shown on screen.

Nothing submits itself

A pause before Submit, a vision check per step, survivor edits and approval, then a fresh microVM for the submit. Only our own mock portal is ever targeted.

Why only Vultr

The track asks for it

"All running on Vultr infrastructure." Model, agent, sandboxes and network all run on Vultr.

One private network

Control plane, sandbox host and mock sites share one Vultr VPC. A second cloud would mean public links between providers: more ways in.

Keys and data stay put

Inference runs on Vultr too, so photos, keys and model calls never go to a third party.

VX1 runs microVMs

Hardware virtualization on VX1 gives each job its own kernel: stronger isolation than containers.

"Everything — model, agent, sandboxes, network — runs inside one Vultr private network. The only things exposed are the web app and the model API. That is what Blast Radius Zero means to us."

Honest limits

  • The 3D comes from one photo with an AI depth model, not LiDAR or multi-view. Measurements are estimates, ±25%.
  • The aid portal and the scam site are our own mocks. The agent never touches a real government site.
  • Next steps: a multi-view scan from a phone video (script written, OpenDroneMap on Vultr CPU), rate limits and cost caps, login with per-session URLs.
